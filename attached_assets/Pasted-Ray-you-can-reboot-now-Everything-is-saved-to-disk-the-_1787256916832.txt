  The webhook bug (#175) — root cause found and proven

  Your option (a) was right, with a specific culprit: the Zod schema requires every transcript item's
  message to be a string, but ElevenLabs sends message: null on tool-call turns — and Jessica has voice
  tools she invokes mid-call. One null fails the parse of the entire payload, which hits the silent
  {received: true} branch, so any call where Jessica used a tool never finalized; plain conversations
  did. That's the intermittency. I proved it against a real stuck call: the old schema fails at
  data.transcript[2].message ("Expected string, received null"), the fixed schema passes. ElevenLabs'
  webhook status shows zero delivery failures ever — because we always answered 200 — which rules out
  signature/secret issues and confirms the drop was ours.

  Two secondary contributors, both visible in the data: calls placed from the dev workspace write their
  session to the dev DB while the webhook hits the prod deployment (no matching row → silent no-op; all
  24 dev-DB sessions are stuck this way), and the conversation-id backfill was a separate UPDATE after
  the INSERT, so a crash between them left the one unlinkable NULL-id row you saw. The race you
  hypothesized in (c) is real in shape but wasn't the driver — the webhook arrives minutes after the
  backfill.

**How to apply:** at the start of any session that will edit code, run the read-only git proof block (`pwd`, `git rev-parse --show-toplevel`, `git branch --show-current`, `git remote -v`, `git status --short`, and `git fetch origin` + `git log origin/master..master --oneline` to see local-only commits) and report what you find before proceeding — don't assume a prior session's "how many commits ahead" still holds. As of 2026-08-14, Ray chose "hold off on further edits" pending his own sync of this workspace with canonical — check with Ray before resuming normal direct-edit behavior in this repo; do not silently revert to editing as usual.

**Commit author name proves nothing here — verify by content diff, not signature.** Replit's platform auto-checkpoint re-stamps ANY saved working-tree state (a task agent's work, another tool's push pulled into this workspace, manual edits) under the generic "Replit Agent" identity, regardless of true origin. Seeing "Replit Agent" (or a mismatched identity like a prior "LedgerGhost90" commit that Ray confirmed was actually his own) on a commit is not evidence either way about who wrote the code. When asked "did X's work actually land," never answer from `git log` authorship alone — pick a real timestamped baseline commit and run `git diff --stat <baseline>..origin/master` (or HEAD, if synced) to see actual files/line-counts changed, then spot-check that the claimed new files have substantive (non-stub) content. Concluding "nothing landed" from authorship alone was a real mistake made in this repo — content diff told the opposite, correct story.
